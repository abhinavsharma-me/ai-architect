## My understanding

### The idea

The main idea behind DDD, Clean Architecture, and Hexagonal Architecture is to keep business logic independent from infrastructure and external technologies.

In an enterprise AI platform, business rules may change frequently, while infrastructure can change independently.

For example:
- We may switch from one LLM provider to another.
- We may migrate from PostgreSQL to another database.
- We may replace a queue or workflow engine.
- We may introduce new API frameworks.

These changes should not require rewriting our core business rules.

The architecture should allow business logic to remain stable while infrastructure evolves around it.

**The central principle: Business logic should not depend on external technologies.**

### Why it matters

Without proper architectural boundaries, the application becomes tightly coupled.

For example, when business logic directly imports an OpenAI SDK object, it becomes dependent on:
- OpenAI's response structure.
- Provider-specific request formats.
- SDK versions and changes.
- Provider-specific errors and behavior.

If we later switch to Anthropic or AWS Bedrock, we may have to modify our business logic.

This creates several problems:

1. **Vendor lock-in:** Changing providers becomes difficult.
2. **Testing difficulties:** Business logic requires complex infrastructure mocks.
3. **Tight coupling:** Changes in one component affect unrelated components.
4. **Poor maintainability:** Business rules become mixed with database and API logic.
5. **Transaction problems:** Slow external calls can keep database connections and locks occupied.

A good architecture isolates these concerns.

### How it works

#### 1. Strategic Domain-Driven Design (DDD)

Strategic DDD focuses on understanding the business and dividing a large system into meaningful boundaries.

**A. Bounded Context**

A Bounded Context is a boundary within which a particular domain model and its terminology are valid.

For example, an enterprise AI platform might have:

- Document Management
- Risk Evaluation
- Tenant Management
- Billing

Each context owns its own business rules and data model.

The same word may have different meanings in different contexts. Bounded Contexts prevent these models from becoming unnecessarily mixed.

**B. Ubiquitous Language**

Ubiquitous Language means using a common vocabulary between developers, architects, and business experts.

For example:

- `ContractReview`
- `ClauseRiskAssessment`
- `ApprovalGate`
- `TenantQuota`

Instead of using vague names such as `Item`, `Data`, or `AIResult`, we use terms that represent actual business concepts.

The purpose is to make code and business discussions speak the same language.

**C. Context Mapping**

Context Mapping describes how different Bounded Contexts communicate and relate to one another.

Important patterns:

- **Anti-Corruption Layer (ACL):** Translates external or upstream models into our own internal domain language. It prevents external models from contaminating our domain.
- **Published Language:** A shared, documented, and versioned communication format between contexts, such as an API schema or event schema.
- **Conformist:** One context adopts the upstream context's model rather than building a translation layer. This may be reasonable when there is little benefit in maintaining a separate model.
- **Shared Kernel:** A small set of shared domain concepts jointly maintained by multiple contexts. It should remain small to avoid excessive coupling.

An AI adapter can act as an Anti-Corruption Layer by converting provider-specific requests and responses into our own canonical models.

#### 2. Tactical Domain-Driven Design

Tactical DDD focuses on the actual building blocks used to implement a domain model.

**A. Entity**

An Entity is an object whose identity matters, even when its attributes change.

Example:

`ContractReview(id="CR-101", status="PENDING")`

Even if its status changes from `PENDING` to `APPROVED`, it remains the same Entity.

Key characteristics:
- Has a unique identity.
- Can change over time.
- Has a lifecycle.
- Identity determines whether two instances represent the same object.

**B. Value Object**

A Value Object is defined by its attributes rather than an independent identity.

Examples:
- `Money(amount=1000, currency="INR")`
- `RiskScore(value=85, rationale="High exposure")`
- `TokenBudget(max_tokens=4000, max_cost_usd=0.5)`

Key characteristics:
- Usually immutable.
- Has no independent identity.
- Equality is based on its values.
- Can be replaced with another equivalent value.

**Difference:**

| Entity | Value Object |
|---|---|
| Has identity | No independent identity |
| Can change over time | Usually immutable |
| Identity determines equality | Attributes determine equality |
| Example: ContractReview | Example: RiskScore |

**C. Aggregate and Aggregate Root**

An Aggregate is a group of related Entities and Value Objects that must maintain consistency together.

The Aggregate Root is the main entry point through which external objects interact with that Aggregate.

For example:

A `ContractReview` Aggregate may contain:
- Contract review status.
- Clause assessments.
- Risk score.
- Approval state.

The ContractReview Aggregate Root controls modifications and enforces business invariants.

External objects should interact through the Aggregate Root rather than directly modifying its internal objects.

**Important principle: One Aggregate Root generally represents one ACID transaction boundary.**

**D. Reference Aggregates by ID**

When one Aggregate needs to refer to another Aggregate, use its ID rather than holding the entire object reference.

For example:

Prefer:

`tenant_id: TenantId`

Instead of:

`tenant: Tenant`

Why?

- Reduces coupling between Aggregates.
- Prevents accidental modification of another Aggregate.
- Avoids unnecessary object loading.
- Helps keep transaction boundaries separate.
- Makes independent scaling and service extraction easier.

#### 3. Hexagonal Architecture — Ports and Adapters

Hexagonal Architecture places the business application at the center and external technologies at the boundaries.

The main idea is to isolate the core from infrastructure.

**A. Ports**

A Port is an interface that defines what the application needs or exposes.

Examples:
- `LLMInferencePort`
- `ContractRepositoryPort`
- `AuditLogPort`

A Port describes the expected behavior without specifying the concrete technology.

For example, an LLM Port may accept a canonical `LLMRequest` and return an `LLMResponse`.

**B. Adapters**

An Adapter implements a Port and connects the application to a particular external technology.

Examples:
- `OpenAIAdapter`
- `BedrockAdapter`
- `PostgresContractRepository`

The Adapter translates internal application models into provider-specific requests and converts external responses back into internal models.

**C. Inbound and Outbound Adapters**

Inbound (Driving) Adapters bring requests into the application.

Examples:
- FastAPI REST endpoints.
- Temporal workers.
- CLI commands.

Outbound (Driven) Adapters allow the application to communicate with external systems.

Examples:
- LLM providers.
- PostgreSQL.
- S3 storage.
- External APIs.

**Remember:**

- Inbound = Requests enter the application.
- Outbound = The application communicates with external systems.

**D. Dependency Inversion Principle (DIP)**

The Dependency Inversion Principle states that high-level business logic should not depend directly on low-level infrastructure.

Instead, both should depend on abstractions.

For example:

The application depends on `LLMInferencePort`, not directly on `OpenAIAdapter`.

The OpenAI and Bedrock adapters implement that Port.

This allows us to replace the implementation without changing the business logic.

An important distinction:

- Runtime control flow describes which component calls another.
- Source-code dependency direction describes which modules import or depend on other modules.

The runtime may reach an external adapter, but source-code dependencies should still point inward toward the core abstractions.

#### 4. Clean Architecture

Clean Architecture organizes the application into layers based on responsibility.

The important layers are:

**A. Domain Layer**

Contains:
- Entities.
- Value Objects.
- Aggregate Roots.
- Domain Services.
- Domain Events.
- Domain Exceptions.

It contains the core business rules.

It should not depend on:
- FastAPI.
- SQLAlchemy.
- OpenAI SDK.
- Database drivers.
- External APIs.

**B. Application Layer**

Contains:
- Use Cases.
- Application Services.
- Port interfaces.
- Workflow orchestration.

It coordinates business operations and communicates with external systems through Ports.

**C. Infrastructure Layer**

Contains:
- Database implementations.
- LLM adapters.
- External API clients.
- Storage implementations.
- Framework-specific integrations.

It implements the interfaces required by the application.

**Important distinction:**

- Entities enforce business invariants.
- Use Cases orchestrate workflows.
- Domain Services handle domain logic that does not naturally belong to one Entity.

For example, an application service may load data, call an AI Port, invoke a Domain Service, update an Aggregate, and save it.

#### 5. Domain Service vs Application Service

**Domain Service**

A Domain Service contains business logic that does not naturally belong to a single Entity or Value Object.

Example:

A `ConflictOfInterestChecker` that evaluates relationships between multiple business entities.

Characteristics:
- Contains domain rules or calculations.
- Usually stateless.
- Should not perform database or network I/O.
- Should not depend on infrastructure SDKs.

**Application Service**

An Application Service coordinates a complete business workflow.

Example:

1. Load a document.
2. Call an AI Port.
3. Apply the returned result.
4. Save the updated Aggregate.
5. Publish a domain event through the Outbox mechanism.

Characteristics:
- Orchestrates operations.
- Coordinates repositories and Ports.
- Manages workflow sequencing.
- Does not own the core business invariants.

**Remember: Domain Services perform domain logic; Application Services coordinate workflows.**

#### 6. Database Transactions and ACID

A database transaction groups operations so that they succeed together or are rolled back together.

ACID describes four properties:

- **Atomicity:** All operations succeed, or none do.
- **Consistency:** Database rules and invariants remain valid.
- **Isolation:** Concurrent transactions do not interfere incorrectly.
- **Durability:** Committed changes remain saved even after a failure or restart.

For example, saving an analysis may involve:
- Updating the risk score.
- Updating the status.
- Saving the analysis timestamp.

These operations should be committed together.

**Aggregate Transaction Boundary**

One Aggregate Root generally represents one ACID transaction boundary.

Changes inside an Aggregate should be strongly consistent within its transaction.

Different Aggregates should generally not be updated through one large transaction.

Instead, they can communicate asynchronously through Domain Events.

#### 7. Optimistic Locking

Optimistic Locking prevents one user from silently overwriting another user's newer changes.

It commonly uses a `version` field.

Example:

1. Two users read an Aggregate at version 1.
2. User A updates it and saves version 2.
3. User B tries to save using version 1.
4. The database rejects the stale update.
5. User B reloads the latest version and handles the conflict.

A database update can use a condition such as:

`WHERE id = '123' AND version = 1`

If the version has already changed, no row is updated.

This prevents lost updates.

#### 8. Why Database Transactions Should Be Short

A common mistake is keeping a database transaction open while waiting for an external LLM call.

LLM requests can take several seconds.

Keeping a transaction open during that time can:
- Occupy database connections.
- Hold row locks.
- Block other writers.
- Exhaust connection pools under concurrency.

**Correct approach:**

1. Open a short transaction and fetch the required data.
2. Close the transaction.
3. Call the external LLM outside the transaction.
4. Open a new short transaction.
5. Reload the Aggregate.
6. Check its current version and business rules.
7. Save the result and commit.

This keeps database transactions short and reduces unnecessary contention.

#### 9. Transactional Outbox Pattern

The Transactional Outbox pattern solves the problem of reliably publishing events after saving business data.

**The dual-write problem**

Suppose an application:

1. Saves an Aggregate to PostgreSQL.
2. Publishes an event to a message broker.

What happens if the database save succeeds but event publishing fails?

The business data is saved, but other contexts never receive the event.

This creates inconsistency.

**The solution: Transactional Outbox**

Instead of publishing the event immediately, save it in an Outbox table in the same database transaction as the Aggregate update.

For example:

- Update the Aggregate.
- Insert a `DomainEvent` into the Outbox table.
- Commit both together.

A background publisher then:
1. Reads unpublished events.
2. Sends them to the message broker.
3. Marks them as published after successful delivery.
4. Retries failed deliveries.

Even if the event broker is unavailable, the event remains stored in the database.

**Idempotent Consumers**

An event may be delivered more than once.

An idempotent consumer ensures that processing the same event repeatedly does not produce duplicate business effects.

For example, it can record processed event IDs and ignore duplicates.

The Outbox pattern generally provides at-least-once delivery, so consumers must be designed to handle duplicates.

**Eventual Consistency**

Different Bounded Contexts may not update at exactly the same moment.

They become consistent asynchronously as events are processed.

#### 10. Implementing the Architecture in Python

Several Python technologies help implement these patterns.

**A. typing.Protocol and abc.ABC**

Used to define interfaces or Ports.

`typing.Protocol` supports structural typing: a class can satisfy a Protocol by implementing its required methods without explicitly inheriting from it.

`abc.ABC` provides an alternative based on explicit inheritance and abstract methods.

**B. Pydantic and Dataclasses**

Useful for creating structured models and Value Objects.

Pydantic v2 supports `frozen=True` to prevent normal field reassignment.

Examples:
- `LLMRequest`
- `LLMResponse`
- `RiskScore`
- `TokenBudget`

Canonical request and response models prevent provider-specific schemas from entering the domain layer.

**C. Dependency Injection**

Dependency Injection supplies the dependencies required by a class instead of letting the class create them itself.

For example, a Use Case receives:
- `LLMInferencePort`
- `ContractRepositoryPort`

It does not create a specific OpenAI client or database repository internally.

**D. Composition Root**

The Composition Root is where the application's concrete dependencies are created and connected.

For example, the startup module can connect:
- `BedrockAdapter` to `LLMInferencePort`.
- `PostgresContractRepository` to `ContractRepositoryPort`.

The business logic remains independent of those concrete implementations.

**E. Import-linter**

Import-linter or custom AST checks can enforce architectural dependency rules.

For example:
- Domain must not import Infrastructure.
- Domain must not import FastAPI.
- Domain must not import SQLAlchemy.
- Domain must not import OpenAI or Boto3.

These checks can run in CI so architectural violations fail the build.

#### 11. Modular Monolith Structure

A Modular Monolith organizes the application into independent business contexts while keeping them inside one deployable application.

Each Bounded Context can have its own internal layers.

Example:

```text
src/
  contexts/
    document_management/
      domain/
      application/
      infrastructure/

    risk_evaluation/
      domain/
      application/
      infrastructure/

    tenant_management/
      domain/
      application/
      infrastructure/

    billing/
      domain/
      application/
      infrastructure/
```

**Domain**
- Entities
- Value Objects
- Aggregates
- Domain Events
- Domain Exceptions

**Application**
- Use Cases
- Application Services
- Port interfaces
- Workflow orchestration

**Infrastructure**
- Database adapters
- LLM adapters
- Storage adapters
- API and framework integrations

This structure allows each context to evolve independently while maintaining clear boundaries.

### Example

Consider a generic enterprise AI document-analysis platform.

A user uploads a document and requests an analysis.

The architecture works like this:

1. A FastAPI endpoint receives the request.
2. The inbound adapter invokes the application Use Case.
3. The Use Case loads the required Aggregate through a repository Port.
4. The application calls an LLM Port outside the database transaction.
5. The LLM Adapter communicates with the selected provider.
6. The Adapter converts the provider response into a canonical internal response.
7. The application reloads the Aggregate and validates the current version.
8. The Aggregate applies the result while enforcing business invariants.
9. The updated Aggregate and its Domain Event are saved in one transaction.
10. A background publisher sends the event to other contexts.
11. Idempotent consumers process the event.

This gives us a system where business rules remain independent of external technologies and changes can be handled at the boundaries.

## What surprised me

- A system can have clean runtime workflows but still have incorrect source-code dependencies.
- A class does not necessarily need to inherit from a Python Protocol to satisfy it.
- An Aggregate Root is not just a parent object; it defines a consistency boundary.
- A slow LLM call can create database connection and locking problems even when the AI integration itself works correctly.
- Saving an event in an Outbox table is more reliable than directly publishing it after a database commit.
- The Outbox pattern does not guarantee exactly-once delivery. Consumers must handle duplicate events.
- Different Bounded Contexts can become consistent asynchronously rather than requiring one large transaction.
- Architecture rules can be enforced automatically in CI rather than depending only on developer discipline.

## Mistakes and failure modes

**1. Leaky Abstractions**
- Exposing provider-specific fields such as OpenAI-specific `model_kwargs` in a generic LLM Port.
- This makes it difficult to switch providers.
- Solution: Use canonical internal request and response models.

**2. Cross-Aggregate Transaction Coupling**
- Updating multiple Aggregates in one large ACID transaction.
- This increases locking and coupling.
- Solution: Keep transactions scoped to individual Aggregates and coordinate across boundaries using Domain Events and Outbox.

**3. Holding Database Locks During LLM Calls**
- Keeping a PostgreSQL transaction open while waiting for an external AI response.
- This can exhaust connection pools and block other operations.
- Solution: Close the transaction before the external call and open a new short transaction when saving the result.

**4. God Aggregates**
- Putting too many Entities and business responsibilities into one Aggregate.
- This increases contention and optimistic-locking conflicts.
- Solution: Keep Aggregates small and define clear consistency boundaries.

**5. Over-Abstraction**
- Creating too many interfaces, DTOs, and layers for simple operations.
- This adds boilerplate without meaningful benefits.
- Solution: Introduce abstractions where they protect real boundaries or provide useful flexibility.

**6. Anemic Domain Model**
- Keeping Entities as simple data containers while putting all business logic in application services.
- This weakens domain invariant enforcement.
- Solution: Put business rules and state-transition validation inside the appropriate domain objects.

**7. Domain Layer Depending on Infrastructure**
- Importing frameworks, database libraries, or provider SDKs inside the domain layer.
- Solution: Depend on Ports and enforce dependency rules through static checks.

**8. Duplicate Event Processing**
- Assuming every event will be delivered exactly once.
- Solution: Make consumers idempotent and track processed event IDs.
