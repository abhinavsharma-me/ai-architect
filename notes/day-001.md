## My understanding

### The idea

I initially thought that as a software product grows, we should gradually move towards microservices.

But after studying these concepts, I understand that this is not necessarily true.

A monolith can be a perfectly good architecture. The problem starts when its internal boundaries become unclear and everything becomes dependent on everything else.

For example, an enterprise AI platform may have:

- Authentication and tenant management.
- Document ingestion.
- RAG and knowledge retrieval.
- LLM provider integrations.
- Agent orchestration.
- Audit logs.
- Financial controls.
- External enterprise integrations.

If all these responsibilities are mixed together, even a small change can affect several unrelated parts of the application.

The solution is to establish clear boundaries.

I understood four important architectural styles:

**1. Traditional Monolith**

One application containing most or all business functionality, often with unrestricted internal dependencies.

It is simple to start and internal function calls are fast, but without discipline it can become a tightly coupled system.

**2. Modular Monolith**

One codebase, but divided into independent business modules.

Each module owns its responsibilities, internal logic and data access. Other modules communicate through public interfaces rather than accessing private implementation details.

This gives us the simplicity of a monolith while maintaining architectural discipline.

**3. Service-Oriented Architecture (SOA)**

A system organised around larger enterprise services.

It is particularly useful when integrating different enterprise platforms such as ERP, CRM and legacy systems.

Enterprise Service Buses (ESBs) can help coordinate communication between these systems, although centralised integration infrastructure can become a bottleneck.

**4. Microservices**

An application divided into independently deployable services that communicate over a network.

They are useful when different teams need independent ownership, different components need independent scaling, or a particular component requires separate infrastructure or runtime isolation.

However, they introduce network latency, partial failures, distributed tracing, deployment complexity, retries, eventual consistency and other distributed-systems problems.

My understanding is that microservices are not automatically better than a modular monolith.

### Why it matters

Imagine building an enterprise AI platform with eight microservices from the beginning.

Every request might need to travel through several services.

Each service introduces another network dependency, another deployment, another possible failure point and another operational responsibility.

Even if every individual service is reliable, the complete system may become less reliable.

There is also a development cost. Developers need to understand service contracts, distributed tracing, deployment dependencies and communication failures.

For an early-stage enterprise platform, this complexity might not provide enough benefit.

A modular monolith gives us a better starting point:

- Clear business boundaries.
- Faster internal communication.
- Easier local development.
- Simpler transactions where appropriate.
- Less distributed-systems overhead.
- The ability to extract services later.

I also learned that code isolation and runtime isolation are two different things.

A module can be isolated architecturally but still run inside the same process as other modules.

If that process crashes, all modules inside it are affected.

This is why separate worker processes or containers can be useful even when we maintain one codebase.

### How it works

**1. Module boundaries and bounded contexts**

A bounded context is a boundary around a particular business capability, including its rules, terminology and data.

For example, an enterprise AI platform could have:

- `tenant_iam` — identity, tenants, roles and permissions.
- `llm_router` — provider selection and model communication.
- `rag_knowledge` — documents, embeddings and retrieval.
- `orchestrator` — workflow execution and coordination.
- `audit_finops` — audit records and financial controls.

Each module should own its implementation.

Other modules should not directly access its private repositories, database models or internal implementation.

**2. Public contracts**

I understood this using a restaurant example.

Customers can order from the menu, but they don't need access to the kitchen's internal storage or recipes.

Similarly, software modules should expose public contracts.

For example:

- `contracts.py` contains interfaces, DTOs and protocols.
- `service.py` contains business behaviour.
- `internal/` contains repositories, adapters and private models.

If the RAG module needs an access decision, it should communicate through the Tenant IAM module's public interface instead of directly accessing its private database repository.

This is encapsulation and information hiding.

**3. Dependency direction and DAG**

A DAG means Directed Acyclic Graph.

It represents dependencies between components without allowing circular dependencies.

For example:

`Orchestrator → Tenant IAM, RAG, LLM Router, Audit & FinOps`

The lower-level modules should not create circular dependencies on one another.

Circular dependencies make testing, maintenance and future service extraction much harder.

**4. Vendor SDK isolation**

Provider-specific SDKs should not be imported throughout the application.

Instead, vendor-specific implementations should remain inside the LLM Router.

The rest of the application should communicate through a common request/response contract.

This makes provider switching easier and centralises retries, timeouts, routing and cost controls.

**5. In-process calls versus network calls**

A function call inside one process is fundamentally different from an HTTP or gRPC request to another service.

An in-process call is generally much faster and does not introduce a network failure.

A network request introduces:

- Serialization and deserialization.
- Network latency.
- Connection failures.
- Timeouts.
- Partial failures.
- Version compatibility requirements.

One particularly interesting problem is the unknown outcome.

Suppose Service A requests Service B to create a workflow.

Service B successfully creates it, but the response gets lost.

Service A times out.

Now Service A doesn't know whether the workflow was created.

If it blindly retries, it might create a duplicate.

This is where idempotency becomes important.

An idempotency key ensures that repeating the same logical request does not create unintended duplicate effects.

**6. Tail latency**

I learned that average response time is not enough to understand application performance.

We need to understand the slowest requests as well.

- p50: Median response time.
- p95: 95% of requests complete within this time.
- p98: 98% complete within this time.
- p99: 99% complete within this time.

For example, a p99 latency of 5 seconds means 99% of requests finish within 5 seconds, while the slowest 1% take longer.

When we chain multiple services together, the probability of encountering at least one slow component increases.

If each service has an independent probability `p` of experiencing a particular stall, then:

`P(at least one stall) = 1 - (1-p)^N`

For a 1% stall probability per service:

| Chained services | Probability of at least one stall |
|---:|---:|
| 1 | 1.00% |
| 10 | 9.56% |
| 30 | 26.03% |

This is a simplified model assuming independent stall events.

**7. Composite availability**

If every service in a serial request path must be available, the overall availability is the product of individual availabilities.

`A_total = A₁ × A₂ × ... × Aₖ`

For eight services, each with 99.9% availability:

`0.999^8 ≈ 0.992028`

That means approximately 99.20% end-to-end availability.

For a 30-day month:

`Downtime = (1 - Availability) × 720`

At 99.20% availability, this is approximately 5.76 hours of expected monthly downtime.

I also worked through an assessment involving seven services, each with 99.8% availability and a 2% chance of a 400ms stall.

Results:

- Composite availability: approximately 98.61%.
- Expected monthly downtime: approximately 10.02 hours.
- Probability of at least one 400ms stall: approximately 13.19%.

The important lesson is that individually reliable components do not automatically create a highly reliable overall system.

**8. Python asyncio and event-loop starvation**

I understood the event loop through the example of a waiter serving multiple tables.

When one customer is waiting for food, the waiter can serve another table.

Similarly, Python's asyncio event loop schedules multiple asynchronous tasks.

When a coroutine reaches an `await` for I/O, it can yield control so other tasks can execute.

This is cooperative multitasking.

However, CPU-heavy synchronous work can block the event loop.

Examples include:

- Parsing large PDFs.
- OCR.
- Image processing.
- Extracting complex tables.
- Large CPU-intensive transformations.

When this happens, other coroutines cannot make progress on that event-loop thread.

This can cause timeouts, stalled streaming responses, delayed health checks and increased p95/p99 latency.

The Linux kernel schedules processes and threads, but it does not automatically schedule Python coroutines inside a blocked event loop.

**9. Isolated worker pools**

The solution is to separate workloads according to their resource requirements.

A possible architecture:

- API Gateway: Receives requests, authenticates, validates and enqueues work.
- Agent Workers: Execute long-running AI workflows.
- Ingestion Workers: Handle PDFs, OCR, extraction, chunking and embeddings.

The API can enqueue a durable job and return HTTP `202 Accepted` with a job identifier.

Different worker pools can use the same codebase and Docker image with different entrypoints and resource limits.

**10. Reliability engineering**

I learned that reliability engineering is about making systems perform their intended functions consistently, anticipate failures, limit their impact and recover within acceptable business targets.

The AWS Reliability Pillar helped me understand reliability through four areas:

- Foundations.
- Workload architecture.
- Change management.
- Failure management.

Foundations include networking, infrastructure capacity, cloud quotas and service limits.

Workload architecture focuses on dependencies, communication, fault isolation, queues and recovery.

Change management focuses on controlled deployments, CI/CD, Infrastructure as Code, canary releases, monitoring and rollback.

Failure management focuses on detecting failures, containing them, recovering from them and preparing for disasters.

**11. RTO and RPO**

These are two important disaster-recovery measurements.

- RTO (Recovery Time Objective): How quickly must the service be restored?
- RPO (Recovery Point Objective): How much recent data can the business afford to lose?

For example:

- RTO = 1 hour.
- RPO = 15 minutes.

The system should aim to recover within one hour while limiting data loss to the last 15 minutes of changes.

**12. Failure-handling mechanisms**

I learned that different failure scenarios require different solutions.

- Timeouts: Limit how long an operation can wait.
- Deadlines: Set the overall completion time for a workflow.
- Retries: Repeat selected temporary failures.
- Exponential backoff: Increase the delay between retries.
- Jitter: Add randomness to retry timing.
- Idempotency: Prevent unintended duplicate effects.
- Circuit breakers: Temporarily stop calling unhealthy dependencies.
- Fallbacks: Use approved alternatives.
- Dead-letter queues: Store jobs that have exhausted their retry policy.
- Graceful degradation: Continue providing a reduced but safe experience when non-essential capabilities fail.

Exponential backoff:

`tₙ = min(t_max, t₀ × 2ⁿ)`

For an initial delay of one second, the approximate retry delays are 1, 2, 4 and 8 seconds.

Retries must respect the overall deadline and budget.

**13. Budget enforcement**

AI workflows have financial constraints as well as time constraints.

An execution context can contain:

- Tenant ID.
- Principal ID.
- Trace ID.
- Workflow ID.
- Roles.
- Data residency region.
- Deadline.
- Maximum budget.
- Amount already spent.

Remaining budget:

`Remaining Budget = Maximum Budget - Spent Budget`

But checking the budget only after an LLM call is insufficient.

The cost has already been incurred.

A production system should estimate or reserve the cost before making the call and reconcile it against actual usage afterwards.

Concurrent calls must also account for budget reservations.

**14. Audit integrity**

I learned about hash chains for linking audit records.

Each record includes a hash of its own data and the previous record's hash.

`Hₙ = SHA256(record_dataₙ || Hₙ₋₁)`

This makes certain forms of tampering detectable.

However, a hash chain alone does not guarantee tamper-proof storage.

We still need durable storage, access controls, integrity verification, retention and backups.

I also understood that mandatory compliance audit records and best-effort operational logs are different things.

For a critical regulated action, the application may need to fail closed if the required audit record cannot be durably committed.

**15. Failure isolation and anti-patterns**

Some important anti-patterns I identified:

- Distributed monolith: Multiple services that still share internal dependencies and must be deployed together.
- Vendor SDK leakage: Provider-specific SDKs imported throughout the application.
- Heavy API processing: Performing expensive PDF processing inside the API event loop.
- Uncontrolled retries: Repeating mutations without idempotency.
- Shared bottlenecks: Scaling workers while leaving a single overloaded database.

The solution is to establish genuine ownership boundaries, isolate heavy workloads and design explicit failure behaviour.

**16. When should we extract a microservice?**

I understood that a growing codebase alone is not a reason to introduce microservices.

Possible review triggers include:

- A RAG subsystem approaching 50 million vectors and requiring independent scaling.
- An organisation growing towards 100+ engineers across approximately 15 autonomous teams.
- Dedicated GPU, CUDA, Rust or C++ runtime requirements.
- A genuine need for independent deployment, scaling or failure isolation.

These are examples from the learning material, not universal industry thresholds.

My rule of thumb:

First isolate code boundaries. Then isolate runtime workloads. Extract network services only when measurable evidence justifies the added complexity.

**17. Distributed systems**

A distributed system is a group of computers cooperating to provide a service.

We need distributed systems for:

- Increasing capacity through parallel processing.
- Tolerating faults through replication.
- Operating across different physical locations.
- Improving security through isolation.

But distribution introduces its own challenges:

- Concurrency and race conditions.
- Complex interactions.
- Performance bottlenecks.
- Partial failures.

I found partial failure particularly important.

One component can fail while the rest of the system continues running. A timeout does not necessarily mean the operation failed.

This is why distributed systems need timeouts, retries, idempotency, health checks and recovery mechanisms.

**18. Storage, communication and computation**

These are three fundamental infrastructure areas:

- Storage: Where and how data is stored.
- Communication: How computers exchange information.
- Computation: Where and how work is executed.

A major goal of distributed infrastructure is to hide distribution complexity from application developers.

A developer should ideally be able to call a simple function such as `await hospital_search(query)` without manually discovering servers, managing network connections or reconstructing distributed results.

**19. Consistency, replication and performance**

Replication means maintaining multiple copies of data.

Consistency defines what behaviour users can expect when reading and writing that data.

For example, if a hospital profile is updated, the next read should ideally return the updated information according to the consistency guarantee of the system.

If one replica has the new value while another still has the old value, a user might receive stale data.

I also learned that fault tolerance, consistency and performance involve trade-offs.

Communication and coordination can improve consistency and fault tolerance, but they also introduce overhead.

Different operations can require different consistency guarantees.

For example, hospital administrative updates may require strong consistency, while search index updates may tolerate a short delay.

**20. MapReduce**

MIT's first distributed systems lecture introduced MapReduce.

Its central idea is to divide large computations into smaller tasks and distribute them across multiple machines.

The model follows:

`Map → Shuffle → Reduce`

I understood this through a word-count example.

Input:

- Document 1: apple banana
- Document 2: banana
- Document 3: apple orange

Map produces intermediate key-value pairs:

- Document 1: (apple, 1), (banana, 1)
- Document 2: (banana, 1)
- Document 3: (apple, 1), (orange, 1)

Shuffle groups values by key:

- apple → [1, 1]
- banana → [1, 1]
- orange → [1]

Reduce combines them:

- apple → 2
- banana → 2
- orange → 1

The framework manages task distribution, scheduling, shuffling, failure detection and reassignment.

This lets developers focus on the actual computation.

**21. Google File System and data locality**

MapReduce used Google File System (GFS) for input and output.

The lecture described:

- Files split into 64 MB chunks.
- Chunks distributed across servers.
- Data replicated across two or three servers.
- Multiple workers reading data in parallel.

A major performance concept here is data locality.

Instead of transferring input data across the network, the Coordinator tries to run a Map task on the machine that already stores the input data.

The principle is simple:

Move computation closer to the data whenever practical.

**22. Shuffle, scheduling and fault tolerance**

Shuffle can be expensive because it requires network communication between Map and Reduce workers.

Intermediate data is partitioned using:

`partition = hash(key) % R`

All occurrences of the same key must reach the same Reduce partition.

I also learned about dynamic task scheduling.

Instead of permanently assigning a fixed number of jobs to every worker, the Coordinator gives workers new tasks whenever they finish their previous ones.

This improves utilisation because faster workers naturally complete more jobs.

MapReduce also handles failures by tracking completed tasks and reassigning failed ones.

However, a task may execute twice if the Coordinator incorrectly assumes a worker has crashed.

This is why deterministic Map and Reduce functions are important.

A deterministic function produces the same output for the same input.

I also studied:

- Stragglers: Workers that take significantly longer than others.
- Speculative execution: Running backup copies of unusually slow tasks.
- Atomic rename: Publishing a complete output file instead of exposing partial output.
- Coordinator failure: The Coordinator itself can become a single point of failure.
- Data locality: Avoiding unnecessary network transfers.

An important distinction for AI systems is that LLM calls are not necessarily deterministic. We should therefore persist outputs, use idempotency keys, version prompts and models, validate results and design explicit retry policies.

## What surprised me

- More microservices can actually make a system less reliable.
- A network timeout does not mean that an operation failed. It might have succeeded and only the response was lost.
- A system with a good average response time can still have terrible p99 latency.
- Even services with 99.9% availability can produce approximately 99.20% availability when eight are chained serially.
- The Linux kernel cannot schedule other Python coroutines while the event-loop thread is blocked.
- A modular monolith can have separate runtime worker pools without becoming a microservices architecture.
- A hash chain can detect certain kinds of tampering, but it does not automatically make audit records tamper-proof.
- A retry can execute the same task twice.
- A distributed scheduler can mistakenly classify a slow worker as a failed worker.
- Faster workers can remain underutilised if tasks are assigned in large fixed batches.
- Moving computation closer to stored data can significantly reduce network overhead.
- A system can have perfectly functioning individual components and still fail because of the interactions between them.
- Having backups is not enough. Recovery procedures must actually be tested.

## Mistakes and failure modes

These are the mistakes and architectural problems I particularly want to avoid:

- Choosing microservices simply because the application is growing.
- Creating a distributed monolith where multiple services share internal database dependencies.
- Allowing modules to access each other's private repositories and implementation details.
- Importing vendor-specific SDKs throughout the application.
- Performing CPU-heavy PDF parsing or OCR inside the API event loop.
- Treating module-level separation as equivalent to runtime isolation.
- Assuming a timeout means the original operation did not execute.
- Retrying mutations without idempotency protection.
- Retrying every error without classifying whether it is recoverable.
- Giving every downstream operation a fresh timeout instead of propagating the overall deadline.
- Checking AI spending only after paid provider calls.
- Allowing concurrent workflows to spend the same remaining budget.
- Using an unapproved LLM fallback that violates tenant policy, data residency or privacy requirements.
- Treating a hash chain as a complete audit-security solution.
- Allowing a non-essential service failure to bring down the entire application.
- Degrading the application by bypassing security, tenant isolation or mandatory audit controls.
- Scaling workers without checking whether the database or network is the actual bottleneck.
- Assuming horizontal scaling automatically guarantees high availability.
- Assuming MapReduce retries always execute a task exactly once.
- Ignoring stragglers and uneven workload distribution.
- Treating an untested backup as a reliable disaster-recovery plan.
- Making architecture decisions without documenting their context and trade-offs.
