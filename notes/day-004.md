## My understanding

### The idea

The main thing I understood today is that a system cannot handle unlimited requests.

Every system has limited resources like CPU, RAM, database connections, and workers.

When too many requests arrive at once, the system starts getting slower. Requests begin waiting, queues become bigger, memory gets consumed, and eventually the system can crash.

So, the goal is not just to process requests but also to control how much work enters the system.

### Why it matters

Imagine 1,000 users are using an AI application, and suddenly one enterprise customer uploads 10,000 documents.

If the system tries to process everything at once, it can become overloaded.

This can affect even the users who are just trying to chat with the AI.

That's why we need proper traffic management.

We should know how much work our system can handle, limit unnecessary requests, and make sure important requests are not affected by background jobs.

### How it works

**1. Synchronous Processing**

In synchronous processing, the client sends a request and waits until the server finishes the work and returns the result.

For example, when I call an API to get my user profile, I usually wait for the response.

**2. Asynchronous Processing**

In asynchronous processing, the server accepts the work, saves it, and returns a job ID. The actual work happens in the background.

For example, when someone uploads 10,000 PDFs, we don't need to keep the connection open until all PDFs are processed.

We can return `202 Accepted` with a job ID and let background workers handle the processing.

**3. Little's Law**

The formula is:

`L = λ × W`

- L = Number of requests inside the system.
- λ = Number of requests arriving per second.
- W = Average time a request spends inside the system.

For example, if 100 requests arrive every second and each request takes 5 seconds:

`L = 100 × 5 = 500`

This means around 500 requests are inside the system at a time.

I understood that even if incoming traffic stays the same, slow processing can increase the number of requests inside the system.

**4. Event Loop, Thread Pool and Process Pool**

- Event Loop: Handles many tasks, especially when they are waiting for network or database responses.
- Thread Pool: Helps run blocking operations without blocking the main event loop.
- Process Pool: Useful for CPU-heavy work like processing large PDFs.

One important thing I learned is that heavy CPU work should not run directly inside the event loop because it can block other requests.

**5. Bounded Queues**

A queue stores work that is waiting to be processed.

But if we allow unlimited requests to enter the queue, it can keep growing until the system runs out of memory.

A bounded queue has a fixed limit.

Once it becomes full, the system can stop accepting more work instead of allowing everything to pile up.

**6. Backpressure**

Backpressure means telling the upstream system to slow down because the downstream system cannot handle more work.

For example, if workers are already busy and the queue is full, the API can reject new requests with `429 Too Many Requests` or `503 Service Unavailable`.

**7. Load Shedding**

Sometimes even backpressure is not enough.

In that situation, the system intentionally rejects lower-priority requests to protect important operations.

For example, interactive AI requests should get priority over thousands of background PDF processing jobs.

**8. Noisy Neighbor Problem**

This happens when one customer uses too many resources and affects other customers.

We can solve this using per-tenant rate limits, token buckets, and fair queuing.

Every customer should get a fair share of the available resources.

**9. Retry with Exponential Backoff and Jitter**

If a server is overloaded, clients should not keep retrying immediately.

They should wait before trying again.

The waiting time increases with every retry, and a little randomness is added so all clients don't retry at the same time.

This helps prevent another traffic spike.

### Example

Imagine I am building an enterprise AI platform.

One customer uploads 10,000 PDFs while 500 other users are chatting with the AI.

If everything goes into the same processing queue, the PDF jobs might occupy all the available workers and make chat responses very slow.

Instead, I would:

- Accept PDF uploads asynchronously.
- Put them into a separate background queue.
- Use dedicated workers for document processing.
- Keep interactive requests on a separate, higher-priority path.
- Set limits on how many requests each customer can send.
- Use bounded queues and concurrency limits.
- Reject excess background traffic when the system is overloaded.

This way, one customer's bulk upload doesn't affect everyone else.

## Mistakes and failure modes

- Using an unbounded queue can eventually exhaust system memory.
- Running CPU-heavy work directly inside the Event Loop can block other requests.
- Putting interactive requests and background jobs into the same queue can cause unnecessary delays.
- Allowing one tenant to consume all available resources creates the noisy neighbor problem.
- Retrying requests immediately after a `503` can increase traffic and make the problem worse.
- If health checks get stuck behind normal user traffic, the infrastructure might restart healthy but overloaded servers.
- Accepting too much work without checking system capacity can lead to cascading failures.
