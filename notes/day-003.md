## My understanding

### The idea

Today I learned how different parts of a software system communicate with each other.

Let's imagine we are building an AI chatbot like ChatGPT.

When a user asks a question, the request doesn't directly go to the AI model.

It passes through different parts of the system.

For example:

1. The user sends a question from their browser.
2. A Load Balancer distributes incoming traffic.
3. The API Gateway checks the request and decides where it should go.
4. The backend processes the request.
5. Different internal services communicate with each other.
6. The AI model generates an answer.
7. The answer is sent back to the user.

I understood that all these technologies have different responsibilities, but they work together to make an application fast, secure, and reliable.

### Why it matters

Imagine thousands of people using an AI application at the same time.

Without proper architecture:

- Servers can become overloaded.
- Requests can go to the wrong service.
- Unauthorized people might access private data.
- Users might experience very slow responses.
- The application might crash when traffic increases.
- We might waste money generating AI responses that nobody receives.

Companies use these technologies to prevent such problems.

The goal is to build software that can handle many users, communicate safely, and continue working even when something goes wrong.

### How it works

**1. Load Balancer**

A Load Balancer is like a manager who distributes work among multiple employees.

Imagine a restaurant with five waiters and 100 customers.

Instead of sending all 100 customers to one waiter, the manager distributes them among all five.

A Load Balancer does the same thing with incoming requests. It distributes traffic among different servers.

There are two important types:

- **L4 Load Balancer:** It looks at the IP address and port. It doesn't understand the actual HTTP request.
- **L7 Load Balancer:** It understands HTTP requests and can make decisions based on URLs, headers, and other request information.

For example, L7 can send `/chat` to the Chat Service and `/payment` to the Payment Service.

**2. TLS and mTLS**

TLS protects information while it travels across the internet.

Imagine putting your message inside a locked box so that other people cannot read it.

TLS helps keep communication encrypted.

mTLS stands for Mutual TLS.

In normal TLS, the client verifies the server's identity. In mTLS, both sides verify each other's identity.

This is useful when different internal services need to communicate securely.

**3. API Gateway**

An API Gateway is like a receptionist at the entrance of a company.

Every visitor first comes to the receptionist, who checks their identity and directs them to the correct department.

An API Gateway does something similar.

Its main responsibilities are:

- **Authentication:** Checks whether the user is allowed to make the request.
- **Routing:** Sends the request to the correct backend service.
- **Rate Limiting:** Controls how many requests a user can send.
- **Security:** Helps protect internal services.
- **Timeout Management:** Controls how long the system waits for a response.

I also learned about JWT.

JWT is like a digitally signed identity card that carries information about a user. The gateway can validate it before allowing a request to continue.

**4. Canary Deployment**

Imagine a company launches a new version of its application.

Instead of sending all users to the new version immediately, the company first sends a small percentage of users to it.

For example:

- 95% users use the old version.
- 5% users use the new version.

If everything works properly, the company gradually increases traffic to the new version.

This is called Canary Deployment.

It reduces the risk of releasing a buggy update to everyone.

**5. REST, gRPC, and SSE**

I learned that these are different ways of communication between applications and services.

- **REST:** Usually works through HTTP requests and JSON responses. It is commonly used for login, registration, payments, and normal APIs.
- **gRPC:** A communication framework commonly used between internal services. It uses HTTP/2 and Protocol Buffers to exchange structured data efficiently.
- **SSE:** Allows a server to continuously send updates to a browser over an HTTP connection.

I understood them like this:

REST = Send a request and receive a response.

gRPC = Efficient communication between backend services.

SSE = Receive information continuously from a server.

**6. Protobuf and .proto files**

Protobuf stands for Protocol Buffers.

Instead of sending large amounts of readable JSON, gRPC commonly uses a compact binary format.

A `.proto` file defines the structure of the data and the functions that different services can call.

Think of it as an agreement between two services about how they will communicate.

**7. AI Streaming using SSE**

I learned that AI applications don't always need to wait until the entire answer is ready.

For example, when we ask an AI chatbot a question, we can see the answer appearing gradually.

The server sends small pieces of the answer as they become available.

The browser receives these updates and displays them immediately.

This makes the application feel faster and more interactive.

**8. What happens when a user closes the browser during AI generation?**

Imagine I ask an AI chatbot a question and then close the browser before the answer is complete.

Ideally, the backend should stop generating the answer.

But the backend might continue generating even after the user has disconnected.

This wastes:

- AI tokens and money.
- Server memory.
- Network connections.
- Processing resources.

In FastAPI, we can use `request.is_disconnected()` to check whether the user has disconnected.

If the user has disconnected, we should cancel the ongoing AI generation and release the resources.

**9. OpenTelemetry and Distributed Tracing**

OpenTelemetry helps developers understand what is happening inside an application.

Imagine one request travels through five different services.

If the request becomes slow, how do we find which service caused the delay?

This is where Distributed Tracing helps.

A Trace represents the complete journey of one request.

A Span represents one individual operation during that journey.

I also learned:

- **Trace ID:** Identifies the complete request journey.
- **Span ID:** Identifies one particular operation.
- **Traceparent:** Carries tracing information between services.
- **Baggage:** Carries additional information such as customer ID or workflow ID.
- **Context Carrier:** Helps transfer tracing information when work moves through queues or asynchronous systems.

**10. Managing heavy traffic (SRE)**

SRE stands for Site Reliability Engineering.

Its goal is to make software reliable and keep it working properly.

I learned that CPU usage alone cannot tell us whether a server is healthy.

For example, a server might have low CPU usage but still be holding thousands of open connections while waiting for AI responses.

So we should also monitor:

- Number of ongoing requests.
- Number of requests waiting in a queue.
- Memory usage.
- Open network connections.

I also learned about Graceful Degradation.

It means that when a system becomes overloaded, it should reject extra requests instead of accepting unlimited work and eventually crashing.

Two important HTTP status codes:

- **429:** Too Many Requests.
- **503:** Service Unavailable.

The `Retry-After` header can tell the client how long to wait before trying again.

### Example

Imagine I am building an AI chatbot for a company.

A user asks:

"Summarize my company's financial report."

This is what happens:

1. The user sends the question from the browser.
2. The Load Balancer distributes the incoming traffic.
3. The API Gateway checks the user's JWT and permissions.
4. The gateway sends the request to the FastAPI backend.
5. FastAPI communicates with internal services.
6. gRPC can be used to communicate with embedding and reranking services.
7. The AI model generates the final answer.
8. SSE sends the answer to the browser gradually.
9. OpenTelemetry tracks the request so developers can identify delays or errors.

Now imagine the user closes the browser during generation.

The backend detects the disconnection and cancels the AI generation to avoid wasting resources.

This example helped me understand how all the technologies work together in a real application.

## Mistakes and failure modes

- Sending all incoming traffic to one server instead of distributing it can overload that server.
- Using an L4 Load Balancer when HTTP-level routing is required will not work because L4 cannot understand HTTP paths.
- If TLS is not handled properly, communication between services may not be secure.
- If an API Gateway buffers the entire AI response, users may receive all the generated text at once instead of seeing it gradually.
- If rate limiting is missing, one user can send too many requests and affect other users.
- If an AI generation continues after the user disconnects, the company wastes tokens and server resources.
- If a system does not carry tracing information between services, finding the source of a problem becomes difficult.
- If a server accepts unlimited requests during heavy traffic, its memory and connections can become exhausted.
- If gRPC is used everywhere without considering browser compatibility and simplicity, the architecture can become unnecessarily complicated.
